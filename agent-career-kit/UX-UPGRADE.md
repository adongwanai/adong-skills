# 用户体验升级记录

本记录来自冷启动、简历/JD、完整发布三条独立压测。目标用户覆盖校招到资深候选人，功能闭环优先。

## 完整工作流中的主要问题

| 阶段 | 原问题 | 用户影响 | 本次处理 |
| --- | --- | --- | --- |
| 第一次使用 | 开场要求路径、workspace、双方向和多类材料 | 用户不知道先做什么，尚未看到价值就承担配置成本 | 新增中文首次响应、`intake.md` 与 `--stage intake`；任意一种材料即可启动 |
| 初始化 | 自动建立 5000+ 题索引，空档案立即验证失败 | 初始化慢且“第一次成功”不可达 | 初始化改为轻量；题库首次检索时懒索引；intake 阶段可独立通过 |
| 用户分层 | 产品与能力模型默认资深候选人 | 校招项目被资深标准误判，资深要求又不够显式 | 增加 `campus / experienced / senior` 阶段和分层能力标尺 |
| 方向选择 | 强制同时维护、渲染开发和算法两份简历 | 用户只要一份仍需填另一份，容易制造无证据定位 | 两个方向可独立启用；渲染、打包、验证只处理已启用/已请求方向 |
| 普通项目 | 项目进入简历必须同时有 task set、baseline、trace、failure 等六类证明 | 典型校招 RAG/工具项目无法得到任何简历草稿 | `caution/improve` 可进入简历；只有强证据 `pass` 才要求完整 proof 和工件来源 |
| 内容改写 | “生成简历”默认仍保留原文，优化只停在审计报告 | 用户期待的成品与实际交付不一致，增加确认轮次 | 区分 `generate/audit/preserve`；生成默认允许安全提案，最终应用保留确认记录 |
| PDF 首屏 | 目标岗位标题只存在 TeX 注释 | 招聘者看不到岗位定位，验证却误判通过 | 岗位标题渲染到姓名下方，并加入 PDF 文本验证 |
| 内容排序 | renderer 固定科研、实习、项目顺序 | 开发/算法视图声明的重点顺序不生效 | 按当前 view 的 claim 顺序推导章节顺序 |
| JD 投递 | JD 不进入 renderer，新增 JD 后简历不变 | “针对岗位”实际只是公司分析，没有要求-证据-选材闭环 | 新增投递包、JD 摘要哈希、要求映射、缺口、选材理由、草稿/最终快照 |
| 用户确认 | 改写批准只是文档约定，没有机器状态 | Agent 可能把未确认措辞当最终稿 | Agent 改写 bullet 和最终投递请求都需要明确 approval 记录 |
| 产物验证 | `--require-artifacts` 强制简历、作品集、XLSX 全部存在 | 只做简历也会被判“未完成” | 增加 `--require-resumes` 与 `--require-portfolio`，按请求验收 |
| 求职跟踪 | CSV + XLSX 双层产物，依赖专用 Node 表格运行时 | 维护复杂、跨客户端不稳定 | 删除 XLSX 脚本与 CSV 模板，改为一个中文 `application-dashboard.md` |
| 材料导入 | PDF/DOCX 依赖宿主临场读取，无法重放 | 同一材料在不同客户端得到不同起点 | 新增确定性导入器，保留原件、提取文本、生成去重清单 |
| 岗位推进 | 只有单次 JD 投递包，没有长期岗位状态 | 简历完成后不知道今天该做什么 | 新增岗位、事件、面试与 Offer 单一状态源和增量命令 |
| 转化结果 | 只记录表格，不计算真实阶段转化 | 无法判断渠道、岗位和准备动作是否有效 | 按岗位去重生成目标岗位、投递、回复、面试、Offer 漏斗 |
| 下一步 | Agent 每次临场建议，容易被低价值准备占满 | 临近面试和 Offer 截止可能被遗漏 | 自动排序 Offer、面试、回复、投递跟进和岗位扩充 |
| 主界面 | 用户面对 Markdown、JSON 和目录 | 日常使用成本高，状态不易扫描 | 新增响应式中文网页驾驶舱，Markdown 保留为可迁移审阅视图 |
| 错误反馈 | 英文 schema 路径和 Python traceback 直接出现 | 非技术用户不知道下一步动作 | 用户入口脚本改成中文失败摘要；Skill 要求按经历归纳错误，不透传 traceback |
| 安装 | README 同时出现复制与单源安装，容易产生多个不同版本 | Codex/Claude/OpenCode 行为漂移 | README 统一推荐链接到同一目录，复制安装明确需要同步升级 |

## 现在的理想体验

1. 用户提供任意一种材料或一句背景说明。
2. Agent 先返回已读取材料、候选阶段、目标方向和可审阅首版。
3. Agent 只问最多 3 个会显著改变结果的问题。
4. 用户一次性确认事实和改写。
5. 系统只生成当前请求的简历、投递包、作品集或训练产物。
6. 每个产物使用自己的验证门禁。
7. 面试/投递结果写入单一状态源，自动更新 Markdown、网页、漏斗和下一最佳动作。

## 本次未扩展

- 扫描版 PDF 仍需要宿主 OCR 能力；文本型 PDF、DOCX、Markdown、文本、HTML、JSON 和 TeX 已有确定性导入器。
- 没有增加自动海投、招聘网站登录或实时面试辅助。
- 驾驶舱是本地静态网页，不是需要账号或后端的独立 SaaS。
